# What is real in this repo, and what is not

A previous review of this project found the right things: the "live" ClickHouse
MCP integration silently fell back to in-process tools, the UI animated
hard-coded data while claiming to run the real pipeline, and the offline mode
picked fixture rows by substring instead of executing the SQL. This file is the
standing answer to "which parts of the demo are actually doing what they say".

## Verified, and how you can check it yourself

| Claim | How to falsify it |
|---|---|
| The official ClickHouse MCP server really runs and really answers | `boxoffice mcp-check`. It launches `uvx --python 3.11 mcp-clickhouse`, prints the tool names the server advertises, calls `run_query`, and prints the rows. Captured output: `docs/live-proof.txt`. |
| The agent's queries execute against a live ClickHouse | `BOX_TRANSPORT=mcp boxoffice ask "which genres underperformed in 1999 vs 1998?" --no-llm`, or `BOX_TRANSPORT=http` for scan statistics. |
| The offline path executes SQL rather than matching strings | `boxoffice ask "..." --no-llm` runs against SQLite over a committed ClickHouse extract. `SELECT count(*) FROM imdb.movies WHERE 1=0` returns zero rows (`test_offline_engine_evaluates_predicates`). |
| Offline and live produce the same answer | `python scripts/verify_parity.py` compares all three transports cell by cell. Recorded run and caveats: `docs/PARITY.md`. |
| The UI is not painting fake output | `boxoffice serve` and the page turns green and says LIVE; every panel is filled from the JSON the server returned. Opened as a file it turns amber and says "recorded transcript, not live", and that transcript is generated by `scripts/record_transcript.py` from a real run. |
| The guardrails refuse real attacks | `test_table_functions_are_refused`, `test_out_of_scope_tables_are_refused`, `test_settings_override_is_refused`, and the Guardrail scenario in the UI, which shows actual tool return values. |

## Limitations, stated plainly

**Gemini and ADK are wired but not exercised in the shipped demo.** The
supervisor and the three skills are real ADK agents assembled from
`agent-core`, and `boxoffice ask` calls them when Google Cloud credentials are
present. We do not have a funded Vertex AI project attached to this build, so
every number in `docs/`, in the screenshots and in the tests comes from the
keyless grounded router, not from a Gemini run. Without credentials the CLI
prints `LLM path unavailable ...` on stderr and continues. We have not measured
how the model behaves under this prompt set, and we do not claim to have.

**The keyless router is a router, not a language model.** It maps a question to
one of four named SQL templates and abstains on anything else. That is a
deliberate downgrade so the demo can be grounded without a key; it is not
natural-language understanding, and the UI's question list is the honest set of
things it handles.

**The offline snapshot covers 1998 and 1999 only.** 11,239 rows out of the
playground's 388,269 movies. Offline questions about other years return zero
rows and the agent abstains. See `boxoffice/fixtures/SNAPSHOT.md`.

**The live endpoint is a public playground, not a studio warehouse.** It is
ClickHouse's own `sql-clickhouse.clickhouse.com` with the read-only `demo` user,
so anyone can reproduce our results without a key. The data is IMDb catalogue
data. We have not run this against a private ClickHouse Cloud service, and the
credentialled path (`BOX_CLICKHOUSE_HOST` and friends) is therefore untested
against a real paid cluster.

**The MCP path has no scan statistics.** `run_query` returns columns and rows.
`rows_read` and `bytes_read` show `n/a` on that transport rather than a number
we could not obtain. `BOX_TRANSPORT=http` has them.

**`BOX_MCP_TOOLSET=true` is weaker than the default, on purpose.** It hands the
ADK agent the official server's own tools, which means the model talks to
ClickHouse without our data-scope allowlist in between. We ship the guarded
wiring by default and offer the raw one only for comparison.

**No holdout evaluation.** The review asked for a quantified evaluation across a
question set. We have not built one. What we have is a cross-engine parity check
on one query and 35 unit tests; neither measures answer quality over a
distribution of questions.

## Guardrails: what they do and do not stop

`assert_read_only` plus `assert_query_scope` stop writes, multi-statement
payloads, ClickHouse table functions that read remote or local files,
`SETTINGS` overrides, and any table outside the allowlist. They are string and
regex level checks over comment-stripped SQL, not a full SQL parser: a
sufficiently exotic ClickHouse construct could in principle be shaped past them,
which is why the live account is the read-only `demo` user and why
`readonly=1`, `max_result_rows`, `max_result_bytes` and `max_execution_time` are
also enforced server side on the HTTP transport. Defence in depth, not a proof.
